امنیت کلید API یعنی کلید فقط در سمت سرور و در یک مخزن امن اسرار (secret manager) یا متغیر محیطی نگه داشته شود، هر پروژه و محیط کلید خودش را داشته باشد، دسترسی هر کلید به حداقل لازم محدود شود و کلید به‌طور دوره‌ای عوض شود. اگر هم کلیدی نشت کرد، اول ابطالش کنید و بعد سراغ بقیهٔ کارها بروید.

این راهنما برای توسعه‌دهنده، تیم DevOps و مدیر IT نوشته شده است. مثال‌ها دربارهٔ Claude API‌اند، اما همین اصول برای هر API پولی دیگری هم درست است. اگر با خود Claude API آشنا نیستید، [راهنمای Claude API](/blog/claude-api/) نقطهٔ شروع خوبی است.

## کلید API یعنی رمز عبور حساب و کیف پول شما

کلید API یک رشتهٔ ثابت است که با هر درخواست فرستاده می‌شود و به سرور می‌گوید این درخواست از طرف کیست و هزینه‌اش به حساب چه کسی نوشته شود. در Claude API کلید در هدر `x-api-key` یا به‌صورت `Authorization: Bearer` فرستاده می‌شود (مستندات فعلی شکل دوم را ترجیح می‌دهند) و SDKهای رسمی آن را به‌طور خودکار از متغیر محیطی `ANTHROPIC_API_KEY` می‌خوانند.

هر کس کلید شما را داشته باشد، در عمل جای شما می‌نشیند: با اعتبار شما درخواست می‌فرستد، سهمیهٔ نرخ (rate limit) شما را مصرف می‌کند و صورتحساب را بالا می‌برد. برخلاف رمز عبور، کلید معمولاً احراز هویت دومرحله‌ای ندارد و از هر جایی که به اینترنت وصل باشد کار می‌کند. به همین دلیل نشت کلید API یکی از خطاهای امنیتی رایج و پرهزینه در تیم‌های نرم‌افزاری است.

## قاعدهٔ اول: کلید هرگز در مرورگر یا اپ موبایل

هر چیزی که روی دستگاه کاربر اجرا می‌شود، در دسترس کاربر است. کد JavaScript صفحهٔ وب با چند کلیک در ابزار توسعه‌دهندهٔ مرورگر دیده می‌شود و فایل نصبی اپ موبایل را می‌شود باز کرد و رشته‌هایش را خواند. مبهم‌سازی (obfuscation) کد فقط این کار را کمی کندتر می‌کند. مستندات رسمی Anthropic هم توصیه می‌کند Claude API را از بک‌اند خودتان صدا بزنید، نه از کدی که در مرورگر کاربر اجرا می‌شود.

> **هشدار:** SDK رسمی TypeScript گزینه‌ای برای اجرا در مرورگر دارد (`dangerouslyAllowBrowser`) که نامش با `dangerously` شروع می‌شود. این نام عمدی است: فعال کردنش یعنی کلید را در اختیار هر بازدیدکننده‌ای می‌گذارید.

### الگوی پراکسی سمت سرور

راه درست این است که فرانت‌اند یا اپ موبایل به بک‌اند شما درخواست بدهد و بک‌اند، که کلید را دارد، درخواست را به API بفرستد. این لایه فقط مخفی‌کنندهٔ کلید نیست؛ جای مناسبی برای کنترل هم هست: کاربر را احراز هویت می‌کنید، برای هر کاربر سقف درخواست می‌گذارید، مدل و `max_tokens` را سمت سرور تعیین می‌کنید و هر درخواست را ثبت می‌کنید.

```javascript
import express from "express";
import Anthropic from "@anthropic-ai/sdk";

const app = express();
app.use(express.json({ limit: "100kb" }));

// The key never leaves the server: the SDK reads ANTHROPIC_API_KEY.
// requireUser and rateLimitPerUser are your own auth and rate-limit middleware.
const client = new Anthropic();

app.post("/api/assist", requireUser, rateLimitPerUser, async (req, res) => {
  const text = String(req.body.text ?? "").slice(0, 8000);
  try {
    const message = await client.messages.create({
      model: process.env.CLAUDE_MODEL, // chosen by the server, not the client
      max_tokens: 1024,                // output cap enforced server-side
      messages: [{ role: "user", content: text }],
    });
    res.json({ content: message.content });
  } catch (err) {
    console.error("upstream error", err.status); // never log headers or keys
    res.status(502).json({ error: "upstream_error" });
  }
});

app.listen(3000);
```

دقت کنید که کلاینت فقط متن را می‌فرستد. اگر به کلاینت اجازه دهید مدل، `max_tokens` یا system prompt را تعیین کند، پراکسی شما به یک دروازهٔ باز تبدیل می‌شود.

برای اپ‌های iOS و macOS، مستندات Anthropic روشی به نام App Attest معرفی کرده که به نصب‌های اصیل اپ توکن کوتاه‌عمر (یک‌ساعته و فقط برای Messages API) می‌دهد، بدون اینکه کلیدی داخل اپ قرار بگیرد. در بقیهٔ موارد، پراکسی سمت سرور راه پیش‌فرض است.

## کلید را کجا نگه داریم

### متغیر محیطی و فایل `.env` در `.gitignore`

در محیط توسعهٔ محلی، ساده‌ترین روش متغیر محیطی است که معمولاً از فایل `.env` بارگذاری می‌شود. این فایل هرگز نباید وارد git شود. پیش از اولین commit، آن را به `.gitignore` اضافه کنید و یک فایل نمونهٔ بدون مقدار واقعی برای هم‌تیمی‌ها بگذارید:

```bash
# .gitignore
.env
.env.*
!.env.example
```

```bash
# .env.example  (committed, no real values)
ANTHROPIC_API_KEY=
CLAUDE_MODEL=
```

در کد، کلید را فقط از محیط بخوانید و اگر نبود، با خطای روشن متوقف شوید تا برنامه با تنظیمات ناقص بالا نیاید:

```python
import os

from anthropic import Anthropic

if not os.environ.get("ANTHROPIC_API_KEY"):
    raise RuntimeError("ANTHROPIC_API_KEY is not set")

client = Anthropic()  # reads the key from the environment
```

فایل `.env` به‌تنهایی امن نیست؛ فقط از commit شدن کلید جلوگیری می‌کند. هر کسی که به سرور یا لپ‌تاپ دسترسی داشته باشد، فایل را می‌خواند. پس دسترسی فایل را محدود کنید و برای محیط عملیاتی سراغ secret manager بروید.

### Secret manager

در محیط عملیاتی، کلید را در یک secret manager نگه دارید؛ سرویس‌های مدیریت اسرار ابرهای بزرگ، HashiCorp Vault یا ابزار مشابه. مزیت‌ها روشن است: کلید رمزنگاری‌شده ذخیره می‌شود، دسترسی هر سرویس جداگانه تعریف می‌شود، هر بار خواندن کلید ثبت می‌شود و چرخش کلید بدون تغییر کد ممکن است. مستندات Anthropic هم نگهداری کلید در secret manager، چرخش دوره‌ای و غیرفعال کردن هر کلید مشکوک به نشت را توصیه می‌کند.

### Secrets در CI/CD

در خط CI/CD، کلید را در بخش secrets خود ابزار (مثلاً GitHub Actions یا GitLab CI) تعریف کنید، نه در فایل تنظیمات pipeline. کلید CI باید جدا از کلید محیط عملیاتی باشد و فقط به محیط آزمون دسترسی داشته باشد. برای بارهای کاری روی ابرها، Kubernetes یا CI، مستندات Anthropic روش [Workload Identity Federation](https://docs.claude.com/en/docs/manage-claude/workload-identity-federation) را پیشنهاد می‌کند: سرویس با هویتی که ارائه‌دهندهٔ هویت شما صادر کرده، توکن کوتاه‌عمر می‌گیرد و اصلاً کلید ثابتی وجود ندارد که نشت کند.

### Secret scanning

خطای انسانی را با ابزار بگیرید. قابلیت secret scanning و push protection در GitHub یا ابزارهای متن‌بازی مثل gitleaks و trufflehog پیش از commit یا push، رشته‌هایی را که شبیه کلیدند پیدا می‌کنند. کلیدهای Claude API با پیشوند `sk-ant-api` شروع می‌شوند و می‌توانید این الگو را به قواعد اسکنر خود اضافه کنید. اسکن را هم در pre-commit hook روی لپ‌تاپ توسعه‌دهنده‌ها بگذارید و هم در CI روی کل مخزن.

## تفکیک و حداقل دسترسی

### کلید جدا برای هر پروژه و محیط

یک کلید مشترک برای همه چیز، بدترین حالت ممکن است: نمی‌دانید هزینه از کجا می‌آید، با نشت یک سرویس همه چیز در خطر است و برای ابطال کلید باید همهٔ سرویس‌ها را هم‌زمان به‌روز کنید. قاعدهٔ ساده این است که برای هر ترکیب «پروژه × محیط» یک کلید بسازید:

| پروژه | dev | staging | prod |
|---|---|---|---|
| چت‌بات پشتیبانی | کلید ۱ | کلید ۲ | کلید ۳ |
| خلاصه‌سازی اسناد | کلید ۴ | کلید ۵ | کلید ۶ |

با این تفکیک، ابطال کلید یک محیط روی بقیه اثری ندارد و گزارش مصرف به‌تفکیک کلید دقیقاً نشان می‌دهد هزینه مال کدام پروژه است. در Claude API هم می‌شود کلید را هنگام ساخت به یک workspace محدود کرد و مستندات رسمی برای کارهای خودکار و مشترک، کلید «حساب سرویس» (service account) را به‌جای کلید شخصی پیشنهاد می‌کند، چون کلید شخصی با رفتن آن فرد از سازمان از کار می‌افتد. توکن‌های سرورهای MCP هم همین تفکیک را لازم دارند؛ جزئیاتش را در [امنیت سرورهای MCP](/blog/claude-mcp/) نوشته‌ایم.

### حداقل دسترسی: مدل، بودجه، خروجی و زمان

هر کلید فقط باید به همان چیزی دسترسی داشته باشد که کارش لازم دارد:

- **مدل‌های مجاز:** اگر لایهٔ پراکسی یا سرویس مدیریت دسترسی شما امکانش را دارد، برای هر کلید فهرست مدل‌های مجاز تعیین کنید. کلید سرویس دسته‌بندی تیکت به مدل‌های گران‌تر نیازی ندارد. محدودیت مدل هم هزینه را کنترل می‌کند و هم اثر سوءاستفاده را.
- **سقف بودجه:** در همان لایه برای هر کلید یا پروژه بودجهٔ ماهانه و هشدار تعریف کنید تا کلید نشت‌کرده نتواند هزینهٔ بی‌سقف بسازد. جزئیات این کار را در [راهنمای کنترل هزینهٔ API هوش مصنوعی](/blog/ai-api-cost-control/) آورده‌ایم.
- **سقف خروجی:** `max_tokens` را سمت سرور ثابت کنید.
- **عمر و محل استفاده:** در Claude Console می‌توانید هنگام ساخت کلید تاریخ انقضا بگذارید (این تاریخ بعداً قابل تغییر نیست) و با IP allowlisting محدود کنید که کلید فقط از نشانی‌های سرورهای شما کار کند.

کلید جدا برای هر پروژه، همراه با بودجه و مدل‌های مجاز، از ایده‌های اصلی طراحی کلاود ایران است که در مرحلهٔ پیش‌عرضه قرار دارد؛ نمونهٔ آن را در [بخش مزیت‌ها](/#features) و [پیش‌نمایش کنسول](/console.html) ببینید.

## چرخش دوره‌ای کلید بدون قطعی

چرخش (rotation) یعنی جایگزین کردن کلید با کلید تازه، پیش از آنکه نشتی رخ دهد یا کشف شود. دورهٔ چرخش را سیاست امنیتی سازمان تعیین می‌کند؛ هر چه کلید عمر کوتاه‌تری داشته باشد، پنجرهٔ سوءاستفاده از نشت احتمالی کوچک‌تر است. اگر کلید را با تاریخ انقضا ساخته‌اید، Anthropic پیش از انقضا به سازندهٔ کلید ایمیل هشدار می‌فرستد (برای کلیدهای خیلی کوتاه‌عمر این ایمیل فرستاده نمی‌شود)، بعد از انقضا درخواست‌ها خطای ۴۰۱ (`authentication_error`) می‌گیرند و کلید منقضی‌شده دوباره فعال نمی‌شود؛ پس چرخش را در تقویم بگذارید، نه در حافظه.

برای چرخش بدون قطعی این ترتیب را دنبال کنید:

1. کلید تازه را با همان دامنهٔ دسترسی کلید قبلی بسازید.
2. آن را در secret manager جایگزین کنید و سرویس‌ها را به‌تدریج با مقدار تازه راه‌اندازی مجدد کنید.
3. گزارش مصرف را به‌تفکیک کلید پایش کنید تا مطمئن شوید کلید قدیمی دیگر استفاده نمی‌شود.
4. کلید قدیمی را اول **غیرفعال** کنید. در Claude Console غیرفعال کردن برگشت‌پذیر است و اگر سرویسی جا مانده باشد، می‌توانید کلید را موقتاً دوباره فعال کنید.
5. بعد از یک دورهٔ اطمینان، کلید قدیمی را **حذف** کنید. حذف دائمی است.

این فرایند فقط وقتی بی‌دردسر است که کلید در یک جای مرکزی خوانده شود. اگر کلید در ده فایل تنظیمات پخش شده باشد، هر چرخش یک پروژهٔ پرخطاست.

## پایش مصرف و لاگ‌های تمیز

### الگوهای غیرعادی مصرف را زود ببینید

بسیاری از نشت‌ها اول در صورتحساب دیده می‌شوند. به‌جای انتظار برای پایان ماه، مصرف هر کلید را روزانه ببینید و برای این نشانه‌ها هشدار بگذارید:

- جهش ناگهانی تعداد درخواست یا توکن نسبت به میانگین روزهای قبل؛
- مصرف در ساعت‌هایی که سرویس شما فعال نیست؛
- استفاده از مدلی که پروژه هیچ‌وقت به کار نمی‌برد؛
- مصرف کلید محیط dev یا CI در حجم محیط عملیاتی؛
- افزایش ناگهانی خطاهای `429` (رسیدن به سقف نرخ) بدون اینکه ترافیک خود شما بیشتر شده باشد.

API مدیریتی Anthropic گزارش مصرف و هزینه را به‌تفکیک کلید و workspace می‌دهد و فهرست کلیدها را همراه با وضعیت و تاریخ انقضا برمی‌گرداند؛ پس می‌توانید هم پایش مصرف و هم ممیزی کلیدها را خودکار کنید.

### لاگ‌ها و خطاها را از کلید پاک نگه دارید

یکی از راه‌های رایج نشت کلید، لاگ است. هدرهای درخواست را لاگ نکنید، در پیام خطا فقط کد وضعیت و شناسهٔ درخواست را بنویسید و در ابزار گزارش خطا (error tracking) قاعدهٔ حذف هدرهای `Authorization` و `x-api-key` را فعال کنید. کلید را در اسکرین‌شات، تیکت پشتیبانی، پیام‌رسان تیمی یا متن پرامپت هم قرار ندهید. اگر لازم است کلیدی را مشخص کنید، فقط چند نویسهٔ آخر یا شناسهٔ آن را بیاورید.

## وقتی کلید نشت کرد: دستورالعمل واکنش

ترتیب کارها مهم است. پیش از هر تحلیل و جلسه‌ای، جلوی ضرر را بگیرید:

1. **ابطال فوری:** کلید را همین حالا غیرفعال یا حذف کنید. ربات‌ها مخزن‌های عمومی را مدام برای یافتن کلید می‌گردند و کلید منتشرشده ممکن است خیلی زود پیدا شود.
2. **صدور کلید جایگزین:** کلید تازه بسازید و فقط در secret manager قرار دهید. اگر کلید محیط عملیاتی بوده، این دو قدم را با هم و سریع انجام دهید تا قطعی کوتاه بماند.
3. **بررسی مصرف:** گزارش مصرف کلید نشت‌کرده را از زمان احتمالی نشت بررسی کنید: چه مدلی، چه حجمی، در چه ساعتی. اگر مصرف غیرمجاز دیدید، با پشتیبانی ارائه‌دهندهٔ سرویس تماس بگیرید.
4. **یافتن مسیر نشت:** کلید از کجا بیرون رفت؟ commit، لاگ، اسکرین‌شات، دستگاه یک هم‌تیمی یا سرویس شخص ثالث؟ تا مسیر بسته نشود، کلید تازه هم در خطر است.
5. **پاک‌سازی تاریخچهٔ git:** اگر کلید commit شده بود، با ابزارهایی مثل `git filter-repo` آن را از تاریخچه پاک کنید. اما فراموش نکنید که این کار جای ابطال را نمی‌گیرد، چون نسخه‌های کپی‌شده، forkها و cacheها همچنان کلید قدیمی را دارند.
6. **ثبت و یادگیری:** حادثه را مستند کنید و کنترلی اضافه کنید که تکرارش را سخت کند: اسکنر، قاعدهٔ لاگ یا محدودیت دسترسی.

اگر از OpenAI API به Claude مهاجرت می‌کنید، فرصت خوبی است که کلیدهای پخش‌شده در سرویس‌ها را هم جمع کنید و از همان ابتدا برای هر پروژه کلید جدا بسازید. مراحل مهاجرت کم‌ریسک را در [راهنمای مهاجرت از OpenAI به Claude](/blog/openai-to-claude-migration/) آورده‌ایم.

## چک‌لیست ۱۰ بندی امنیت کلید API برای تیم

1. هیچ کلیدی در کد فرانت‌اند، اپ موبایل یا مخزن git نیست.
2. همهٔ درخواست‌ها از پراکسی سمت سرور می‌گذرند و مدل و `max_tokens` را سرور تعیین می‌کند.
3. فایل `.env` در `.gitignore` است و فقط `.env.example` بدون مقدار در مخزن قرار دارد.
4. کلیدهای محیط عملیاتی در secret manager نگهداری می‌شوند و کلیدهای CI در secrets ابزار CI.
5. برای هر پروژه و هر محیط (dev، staging، prod) کلید جدا وجود دارد.
6. هر کلید فقط به مدل‌های لازم دسترسی دارد و بودجه، هشدار و سقف خروجی دارد.
7. کلیدها تاریخ انقضا یا برنامهٔ چرخش مکتوب دارند و چرخش بدون قطعی تمرین شده است.
8. secret scanning در pre-commit و CI فعال است.
9. مصرف هر کلید روزانه پایش می‌شود و برای الگوهای غیرعادی هشدار تعریف شده است.
10. لاگ‌ها هدرهای احراز هویت را ثبت نمی‌کنند و دستورالعمل واکنش به نشت در دسترس همهٔ تیم است.

این چک‌لیست را چاپ کنید یا در ویکی تیم بگذارید و هر سه ماه یک بار مرورش کنید. برای پرسش‌های بیشتر دربارهٔ مدل دسترسی پروژه‌محور، [سؤالات متداول صفحهٔ اصلی](/#faq) را ببینید.

> **نکته:** کلاود ایران سرویسی مستقل و در مرحلهٔ پیش‌عرضه است و وابستگی‌ای به Anthropic ندارد. تاریخ آخرین بازبینی این راهنما ۲ آذر ۱۴۰۵ است؛ جزئیات انواع کلید، انقضا و روش‌های احراز هویت را در [مستندات رسمی احراز هویت Claude API](https://docs.claude.com/en/docs/manage-claude/authentication) ببینید.

## سؤالات متداول

### اگر کلید API لو رفت اول چه کنیم؟
اول کلید را غیرفعال یا حذف کنید و بلافاصله کلید جایگزین را فقط در secret manager قرار دهید. بعد مصرف کلید نشت‌کرده را از زمان احتمالی نشت بررسی کنید، مسیر نشت را پیدا و مسدود کنید و اگر کلید در git بوده، تاریخچه را پاک‌سازی کنید. پاک کردن تاریخچه هیچ‌وقت جای ابطال کلید را نمی‌گیرد.

### می‌شود کلید API را داخل اپ موبایل یا فرانت‌اند گذاشت؟
نه. هر چیزی که روی دستگاه کاربر اجرا می‌شود قابل استخراج است و مبهم‌سازی کد فقط کار را کندتر می‌کند. راه درست این است که اپ به بک‌اند شما درخواست بدهد و بک‌اند با کلیدی که فقط خودش دارد API را صدا بزند و هم‌زمان احراز هویت کاربر، سقف درخواست و سقف خروجی را اعمال کند.

### هر چند وقت یک بار کلید را عوض کنیم؟
عدد ثابتی برای همه وجود ندارد و دوره را سیاست امنیتی سازمان تعیین می‌کند. هر چه عمر کلید کوتاه‌تر باشد، خطر نشت احتمالی کمتر است؛ پس برای کلیدها تاریخ انقضا بگذارید یا برنامهٔ چرخش منظم داشته باشید. علاوه بر آن، با رفتن هر عضو تیم که به کلید دسترسی داشته و با هر شک به نشت، کلید را فوراً عوض کنید.

### آیا فایل .env به‌تنهایی امن است؟
نه. فایل `.env` فقط کمک می‌کند کلید وارد کد و مخزن git نشود، به شرطی که در `.gitignore` باشد. هر کسی که به سرور یا دستگاه توسعه‌دهنده دسترسی داشته باشد، می‌تواند آن را بخواند. برای محیط عملیاتی از secret manager با دسترسی تفکیک‌شده و ثبت رویداد استفاده کنید.
