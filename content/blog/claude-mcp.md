اگر برای هر ابزار تازه، از Jira تا پایگاه دادهٔ سفارش‌ها، یک اتصال اختصاصی به مدل زبانی نوشته باشید، مشکلی را که MCP حل می‌کند خوب می‌شناسید. پروتکل زمینهٔ مدل (Model Context Protocol) یا همان MCP راه استانداردی است که در آن هر ابزار یک بار «سرور» می‌شود و هر برنامهٔ هوش مصنوعی یک بار «کلاینت».

در این راهنما می‌بینیم MCP چیست، دقیقاً چه فرقی با tool use دارد، و بعد یک سرور کوچک با پایتون می‌سازیم و آن را امن به Claude وصل می‌کنیم. بخش آخر برای مدیر فنی است: امنیت سرورهای MCP و چک‌لیست پذیرش آن در تیم.

> **نکته:** کلاود ایران سرویسی مستقل و در مرحلهٔ پیش‌عرضه است و هیچ وابستگی‌ای به Anthropic ندارد. مرجع نهایی جزئیات فنی این مقاله [مستندات رسمی MCP](https://modelcontextprotocol.io) و [مستندات MCP connector در Claude](https://docs.claude.com/en/docs/agents-and-tools/mcp-connector) است.

## MCP چیست؟ تعریف در یک پاراگراف

MCP یک پروتکل باز است که تعیین می‌کند برنامه‌های هوش مصنوعی چطور به ابزارها، داده‌ها و قالب‌های آمادهٔ پرامپت دسترسی پیدا کنند. Anthropic آن را معرفی کرد و بعدتر به بنیاد Agentic AI Foundation، که زیر چتر Linux Foundation فعالیت می‌کند، سپرد. پروتکل فقط زبان مشترکی تعریف می‌کند که با آن یک سرور می‌گوید «این ابزارها و این داده‌ها را دارم» و یک کلاینت می‌تواند آن‌ها را فهرست کند و صدا بزند. پیام‌ها روی `JSON-RPC 2.0` رد و بدل می‌شوند و همین قالب در همهٔ روش‌های انتقال یکسان است.

### چرا به یک پروتکل نیاز بود: مسئلهٔ N×M اتصال

فرض کنید تیم شما سه برنامهٔ هوش مصنوعی دارد: یک دستیار پشتیبانی، یک دستیار کدنویسی و یک ابزار گزارش‌گیری داخلی. هر کدام باید به چهار سیستم وصل شود: پایگاه دادهٔ سفارش‌ها، Jira، مخزن اسناد و سرویس پرداخت. بدون استاندارد، ۳ × ۴ یعنی دوازده اتصال جداگانه می‌نویسید و نگه می‌دارید. با هر برنامه یا سیستم تازه، این عدد ضربی بزرگ می‌شود: مسئلهٔ N×M.

MCP این ضرب را به جمع تبدیل می‌کند. هر سیستم یک بار به شکل سرور MCP پیاده می‌شود و هر برنامه یک بار توانایی کلاینت MCP بودن را پیدا می‌کند. در مثال بالا به‌جای دوازده اتصال، چهار سرور و سه کلاینت دارید و هر سرور جدید بلافاصله در هر سه برنامه قابل‌استفاده است. تشبیه رایجش درگاه USB-C است: یک شکل اتصال، دستگاه‌های بسیار.

### MCP چه چیزی نیست

- **مدل نیست.** MCP هیچ هوشی اضافه نمی‌کند. تصمیم اینکه کدام ابزار و با چه ورودی صدا زده شود، هنوز با مدل است.
- **محصول یا سرویس میزبانی نیست.** یک مشخصات (specification) و چند SDK رسمی است. سرور را خودتان اجرا می‌کنید یا از سرورهای آماده استفاده می‌کنید.
- **جای API را نمی‌گیرد.** سرور MCP معمولاً لایه‌ای نازک روی همان APIهای موجود شماست.
- **فقط مخصوص Claude نیست.** استاندارد باز است و ابزارها و ارائه‌دهندگان دیگر هم آن را پشتیبانی می‌کنند.

## معماری MCP: Host، Client و Server

مستندات رسمی سه نقش تعریف می‌کنند:

- **میزبان (Host):** برنامهٔ هوش مصنوعی که کاربر با آن کار می‌کند، مثل Claude Code، Claude Desktop، یک IDE یا اپلیکیشن خود شما. میزبان مدیریت اتصال‌ها را بر عهده دارد.
- **کلاینت (Client):** قطعه‌ای داخل میزبان که با **یک** سرور ارتباط دارد. میزبان برای هر سرور یک کلاینت جدا می‌سازد.
- **سرور (Server):** برنامه‌ای که زمینه (context) فراهم می‌کند: ابزار، داده یا پرامپت. سرور می‌تواند روی همان ماشین اجرا شود (سرور محلی) یا روی اینترنت باشد (سرور راه‌دور).

### سه قابلیت سرور: Tools، Resources، Prompts

پروتکل سه نوع قابلیت اصلی (primitive) برای سرور تعریف می‌کند. فرق مهمشان این است که چه کسی تصمیم به استفاده می‌گیرد:

| قابلیت | چیست | معمولاً چه کسی فعالش می‌کند | مثال |
|---|---|---|---|
| ابزار (Tools) | تابعی اجرایی که کاری انجام می‌دهد یا داده‌ای زنده برمی‌گرداند | مدل، در جریان گفت‌وگو | `get_order_status`، ساختن تیکت Jira |
| منبع (Resources) | داده‌ای فقط‌خواندنی که با یک URI شناخته می‌شود | برنامهٔ میزبان، برای افزودن به زمینه | محتوای یک فایل، schema پایگاه داده |
| پرامپت (Prompts) | قالب آمادهٔ پرامپت با پارامتر | کاربر، مثلاً از یک منو یا فرمان | «بازبینی کد با معیارهای تیم» |

هر قابلیت متدهای مشخصی دارد: کلاینت با `tools/list` فهرست ابزارها را می‌گیرد و با `tools/call` یکی را اجرا می‌کند. منابع با `resources/read` و پرامپت‌ها با `prompts/get` خوانده می‌شوند. چون فهرست‌ها پویا هستند، سرور می‌تواند ابزارهایش را عوض کند و از طریق اعلان (notification) خبر بدهد. همین ویژگی، چنان‌که در بخش امنیت می‌بینیم، یک ریسک هم هست.

کلاینت هم قابلیت‌هایی دارد، از جمله **درخواست ورودی از کاربر (elicitation)**: سرور می‌تواند وسط کار از کاربر اطلاعات یا تأیید بخواهد.

### انتقال (transport): stdio محلی و HTTP راه‌دور

MCP دو روش انتقال استاندارد دارد:

- **stdio:** میزبان سرور را به شکل یک پردازهٔ فرزند (subprocess) روی همان ماشین اجرا می‌کند و پیام‌ها از ورودی و خروجی استاندارد رد و بدل می‌شوند. برای ابزارهای محلی، مثل دسترسی به فایل‌های پروژه، ساده و سریع است و معمولاً فقط به یک کلاینت خدمت می‌دهد.
- **Streamable HTTP:** کلاینت پیام‌ها را با HTTP POST می‌فرستد و سرور می‌تواند پاسخ را به شکل جریان (Server-Sent Events) برگرداند. این روش سرور راه‌دور است، به کلاینت‌های زیادی خدمت می‌دهد و از روش‌های استاندارد احراز هویت HTTP مثل bearer token پشتیبانی می‌کند. مشخصات MCP گرفتن توکن با OAuth را توصیه می‌کند.

### یک درخواست از اول تا آخر

```text
  user: "what's the status of order A-1042?"
    │
    ▼
┌─────────── MCP Host (Claude Code / your app) ───────────┐
│                                                         │
│   model (Claude) ◀── tool lists ──┐                     │
│        │                          │                     │
│        │ tool call                │                     │
│        ▼                          │                     │
│   ┌──────────────┐   JSON-RPC   ┌─┴────────────┐        │      ┌──────────────┐
│   │ host routes  │────────────▶ │ MCP Client 1 │◀───────┼─────▶│ orders server│──▶ orders DB
│   │  the call    │              ├──────────────┤        │      ├──────────────┤
│   └──────────────┘              │ MCP Client 2 │◀───────┼─────▶│ jira server  │──▶ Jira API
│                                 ├──────────────┤        │      ├──────────────┤
│                                 │ MCP Client 3 │◀───────┼─────▶│ docs server  │──▶ file store
│                                 └──────────────┘        │      └──────────────┘
└─────────────────────────────────────────────────────────┘
   one client per server · same JSON-RPC 2.0 messages over stdio or Streamable HTTP
```

1. میزبان هنگام اتصال، از هر سرور فهرست ابزارهایش را می‌گیرد (`tools/list`).
2. این فهرست، با نام و توضیح و schema ورودی هر ابزار، در اختیار مدل قرار می‌گیرد.
3. مدل تشخیص می‌دهد که برای پاسخ به ابزار `get_order_status` نیاز دارد و ورودی‌اش را می‌سازد.
4. میزبان فراخوانی را به کلاینت همان سرور می‌دهد و کلاینت `tools/call` را می‌فرستد.
5. نتیجه برمی‌گردد، به زمینهٔ مدل اضافه می‌شود و مدل پاسخ نهایی را می‌نویسد.

## فرق MCP با tool use، API و RAG

بیشترین سردرگمی دربارهٔ MCP همین‌جاست، چون هر چهار مفهوم دربارهٔ «وصل کردن مدل به دنیای بیرون» هستند ولی در لایه‌های متفاوتی کار می‌کنند.

### MCP در برابر tool use (function calling)

Tool use، که در OpenAI به آن function calling می‌گویند، سازوکار خود مدل است: در درخواست به Claude API فهرستی از ابزارها با JSON Schema می‌فرستید، مدل با بلوک `tool_use` می‌گوید کدام ابزار را با چه ورودی صدا بزنید، کد شما آن را اجرا می‌کند و نتیجه را با `tool_result` برمی‌گرداند. جزئیات این حلقه را در [راهنمای tool use در Claude](/blog/claude-tool-use/) نوشته‌ایم و اینجا تکرارش نمی‌کنیم.

MCP روی همین سازوکار سوار است و فرقش در این است که ابزار از کجا می‌آید و کجا اجرا می‌شود. در tool use خالص، تعریف و اجرای ابزار داخل اپلیکیشن شماست. در MCP، هر دو در یک سرور جداست که هر میزبانی می‌تواند از آن استفاده کند. به بیان کوتاه: tool use یعنی «مدل چطور تابع را صدا می‌زند» و MCP یعنی «تابع‌ها چطور یک بار و استاندارد عرضه شوند».

### MCP در برابر فراخوانی مستقیم API

اگر فقط یک برنامه دارید که باید به یک سرویس وصل شود، فراخوانی مستقیم API آن سرویس ساده‌ترین راه است. MCP وقتی ارزش پیدا می‌کند که یک قابلیت در چند برنامه یا چند محیط لازم است، یا بخواهید از سرورهای آماده استفاده کنید.

### MCP در برابر RAG (و ترکیب این دو)

بازیابی همراه با تولید (Retrieval-Augmented Generation) یا RAG الگویی برای پیدا کردن تکه‌های مرتبط از اسناد و گذاشتنشان در پرامپت است. RAG دربارهٔ *چه داده‌ای* به مدل برسد و MCP دربارهٔ *از چه راهی* برسد. این دو با هم تضادی ندارند: جست‌وجوی برداری روی اسناد شرکت را می‌شود به شکل یک ابزار در یک سرور MCP عرضه کرد تا هر دستیاری بتواند از آن استفاده کند.

| | Tool use | MCP | API مستقیم | RAG |
|---|---|---|---|---|
| چه چیزی را حل می‌کند | مدل بتواند تابعی را صدا بزند | عرضهٔ استاندارد ابزار و داده به هر برنامه | اتصال یک برنامه به یک سرویس | رساندن متن مرتبط از اسناد به مدل |
| کجا تعریف می‌شود | پارامتر `tools` در درخواست | سرور MCP | کد اپلیکیشن | خط لولهٔ بازیابی و ایندکس |
| کجا اجرا می‌شود | کد اپلیکیشن شما | سرور MCP، محلی یا راه‌دور | کد اپلیکیشن شما | پایگاه برداری و کد شما |
| کی مناسب است | یک برنامه با چند تابع اختصاصی | چند برنامه، چند تیم یا سرور آماده | اتصال یک‌باره و ساده | پرسش و پاسخ روی اسناد زیاد |

## سه راه استفاده از MCP با Claude

### اپ‌های آماده: Claude Desktop و Claude Code

ساده‌ترین مسیر، میزبان‌های آماده‌ای است که خودشان کلاینت MCP دارند. Claude Code و Claude Desktop هر دو می‌توانند به سرورهای محلی (stdio) و راه‌دور وصل شوند. در Claude Code سرور را با فرمان `claude mcp add` اضافه می‌کنید و با `claude mcp list` وضعیت اتصال‌ها را می‌بینید. نمونه‌اش را در بخش بعد، روی سرور خودمان، می‌آوریم. این مسیر برای کار روزمرهٔ توسعه‌دهنده عالی است، ولی جای یکپارچه‌سازی در محصول شما نیست.

### MCP connector در Claude API

اگر محصولتان روی [Messages API در Claude](/blog/claude-api/) ساخته شده، کانکتور MCP (MCP connector) اجازه می‌دهد بدون نوشتن کلاینت MCP، یک سرور راه‌دور را مستقیم در درخواست معرفی کنید. اتصال به سرور را خود API انجام می‌دهد و فراخوانی ابزارها و نتیجه‌هایشان در همان پاسخ برمی‌گردد. دو جزء همیشه با هم لازم‌اند: آرایهٔ `mcp_servers` که آدرس و نام سرور را تعریف می‌کند، و یک ورودی `mcp_toolset` در `tools` که با همان نام به سرور ارجاع می‌دهد. اگر یکی را بدون دیگری بفرستید، درخواست خطای اعتبارسنجی می‌گیرد.

```python
import os
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

response = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    betas=["mcp-client-2025-11-20"],  # check the current header name in the docs
    system="You are a support assistant. Use the orders tools for order questions. Reply in Persian.",
    mcp_servers=[
        {
            "type": "url",
            "url": "https://mcp.example.com/mcp",  # your public HTTPS MCP server
            "name": "orders",
            "authorization_token": os.environ["ORDERS_MCP_TOKEN"],  # never hardcode
        }
    ],
    tools=[
        {
            "type": "mcp_toolset",
            "mcp_server_name": "orders",  # must match the name above
            "default_config": {"enabled": False},          # allowlist mode
            "configs": {"get_order_status": {"enabled": True}},
        }
    ],
    messages=[{"role": "user", "content": "سفارش A-1042 در چه وضعیتی است؟"}],
)

if response.stop_reason == "refusal":
    print("Request was declined.")
else:
    for block in response.content:
        if block.type == "mcp_tool_use":
            print("tool call:", block.server_name, block.name, block.input)
        elif block.type == "mcp_tool_result":
            print("tool error" if block.is_error else "tool ok")
        elif block.type == "text":
            print(block.text)
```

همین درخواست با curl:

```bash
curl https://api.anthropic.com/v1/messages \
  -H "Content-Type: application/json" \
  -H "x-api-key: $ANTHROPIC_API_KEY" \
  -H "anthropic-version: 2026-10-21" \
  -H "anthropic-beta: mcp-client-2025-11-20" \
  -d '{
    "model": "claude-opus-5-5",
    "max_tokens": 16000,
    "messages": [{"role": "user", "content": "سفارش A-1042 در چه وضعیتی است؟"}],
    "mcp_servers": [
      {
        "type": "url",
        "url": "https://mcp.example.com/mcp",
        "name": "orders",
        "authorization_token": "'"$ORDERS_MCP_TOKEN"'"
      }
    ],
    "tools": [
      {
        "type": "mcp_toolset",
        "mcp_server_name": "orders",
        "default_config": {"enabled": false},
        "configs": {"get_order_status": {"enabled": true}}
      }
    ]
  }' | jq '.content[] | {type, name, text}'
```

در پاسخ دو نوع بلوک تازه می‌بینید: `mcp_tool_use` که نام سرور، نام ابزار و ورودی را دارد، و `mcp_tool_result` که نتیجه و فیلد `is_error` را دارد. برخلاف tool use معمولی، لازم نیست خودتان ابزار را اجرا کنید و نتیجه را برگردانید؛ این رفت‌وبرگشت سمت API انجام می‌شود.

بخش `default_config` با `"enabled": false` و فعال کردن تک‌تک ابزارها در `configs` الگوی فهرست مجاز (allowlist) است: فقط ابزاری که صریحاً نام برده‌اید به مدل می‌رسد، حتی اگر سرور فردا ابزار تازه‌ای اضافه کند. الگوی برعکس (denylist) هم ممکن است، ولی برای محیط تولید allowlist امن‌تر است. تعریف هر ابزار فعال هم جزو ورودی درخواست است؛ [توکن ورودی و هزینهٔ تعریف ابزارها](/blog/claude-tokens-pricing/) را در حساب‌وکتاب هزینه در نظر بگیرید.

> **هشدار:** طبق مستندات فعلی، کانکتور از میان قابلیت‌های MCP فقط **فراخوانی ابزار** را پشتیبانی می‌کند (نه منابع و نه پرامپت‌ها)، و سرور باید روی HTTP عمومی با آدرس `https://` در دسترس باشد (Streamable HTTP یا SSE). سرور محلی stdio مستقیم وصل نمی‌شود. اگر سرور OAuth می‌خواهد، گرفتن و تمدید توکن با خود شماست و توکن را در `authorization_token` می‌فرستید. داده‌هایی که از کانکتور رد می‌شوند، از جمله تعریف ابزارها و نتیجه‌ها، طبق سیاست معمول نگه‌داری داده ذخیره می‌شوند و مشمول توافق‌های بدون نگه‌داری داده (ZDR) نیستند.

> **نکته:** آخرین بازبینی: ۵ آذر ۱۴۰۵. مستندات MCP connector دو هدر beta را فهرست کرده‌اند: `mcp-client-2025-11-20` و نسخهٔ تازه‌تر `mcp-client-2026-09-15` که امکان ثابت کردن (pin) فهرست ابزارهای سرور را هم اضافه می‌کند، ولی هنوز روی همهٔ پلتفرم‌ها پذیرفته نمی‌شود. نسخهٔ `mcp-client-2025-04-04` منسوخ است. نام هدرها در دورهٔ beta عوض می‌شود؛ پیش از استفاده [صفحهٔ رسمی MCP connector](https://docs.claude.com/en/docs/agents-and-tools/mcp-connector) را چک کنید.

### کلاینت MCP خودتان با SDK

اگر سرورتان محلی است، به منابع و پرامپت‌ها هم نیاز دارید، یا می‌خواهید کنترل کامل اتصال دست خودتان باشد، کلاینت را در اپلیکیشن خودتان می‌سازید. در این حالت اپلیکیشن شما میزبان است: با SDK رسمی MCP به سرور وصل می‌شود، ابزارها را به شکل ابزار معمولی به Claude API می‌دهد و فراخوانی‌ها را خودش به سرور می‌فرستد. SDK پایتون Anthropic برای این کار تابع‌های کمکی دارد (`pip install "anthropic[mcp]"`) که با tool runner کار می‌کنند. نمونه‌های بیشتر از ساختار API را در [بخش توسعه‌دهندگان](/#developers) گذاشته‌ایم.

## ساخت یک سرور MCP کوچک با پایتون

حالا سرور سفارش‌ها را می‌سازیم: دو ابزار فقط‌خواندنی که وضعیت یک سفارش را برمی‌گردانند یا سفارش‌ها را بر اساس وضعیت فهرست می‌کنند. از SDK رسمی پایتون MCP استفاده می‌کنیم که به پایتون ۳٫۱۱ یا بالاتر نیاز دارد:

```bash
pip install "mcp[cli]"      # or: uv add "mcp[cli]"
```

بستهٔ `cli` فرمان `mcp` را اضافه می‌کند که برای تست لازم داریم.

### تعریف ابزار با `@mcp.tool()` و docstring

```python
"""Minimal read-only MCP server: order lookups for a support assistant."""
import sys

from mcp.server import MCPServer

mcp = MCPServer(
    "orders",
    instructions="Read-only access to order status. Never invent order data.",
)

# Demo data. In production, query a read-only replica with a read-only DB user.
ORDERS = {
    "A-1042": {"status": "shipped", "updated": "2026-11-24"},
    "A-1043": {"status": "processing", "updated": "2026-11-25"},
    "A-1044": {"status": "shipped", "updated": "2026-11-25"},
}


@mcp.tool()
def get_order_status(order_id: str) -> dict:
    """Look up the current shipping status of one order by its ID, e.g. A-1042."""
    key = order_id.strip().upper()
    order = ORDERS.get(key)
    if order is None:
        return {"order_id": key, "found": False}
    return {"order_id": key, "found": True, **order}


@mcp.tool()
def list_orders_by_status(status: str, limit: int = 10) -> list[dict]:
    """List orders with a given status ('processing' or 'shipped'). Returns at most 50."""
    limit = max(1, min(limit, 50))
    matches = [
        {"order_id": oid, **data}
        for oid, data in ORDERS.items()
        if data["status"] == status.strip().lower()
    ]
    return matches[:limit]


if __name__ == "__main__":
    if "--http" in sys.argv:
        # Remote mode: serves Streamable HTTP at http://127.0.0.1:8000/mcp
        mcp.run(transport="streamable-http", host="127.0.0.1", port=8000)
    else:
        # Local mode: the host starts this script and talks over stdin/stdout
        mcp.run(transport="stdio")
```

چند نکته در همین کد کوتاه هست. اول، schema ورودی را دستی ننوشتیم: نوع پارامترها (`order_id: str`، `limit: int`) همان schema است و SDK آن را می‌سازد. دوم، docstring همان توضیحی است که مدل می‌بیند و بر اساسش تصمیم می‌گیرد کی ابزار را صدا بزند؛ آن را مثل مستندات یک API عمومی، دقیق و بدون ابهام بنویسید. اصول نوشتن توضیح خوب و [system prompt برای هدایت استفاده از ابزار](/blog/claude-prompt-engineering/) را جدا نوشته‌ایم. سوم، ابزارها محدودیت دارند: `limit` سقف دارد و هیچ ابزاری چیزی را تغییر نمی‌دهد.

> **نکته:** طبق راهنمای مهاجرت رسمی، نسخهٔ ۲ این SDK (شاخهٔ پایدار فعلی) کلاس `FastMCP` را به `MCPServer` تغییر نام داده و README رسمی همان `from mcp.server import MCPServer` بالا را به کار می‌برد. اگر در آموزش‌های قدیمی‌تر `from mcp.server.fastmcp import FastMCP` دیدید، آن کد مال نسخهٔ ۱ است و در نسخهٔ ۲ خطای `ModuleNotFoundError` می‌دهد. دکوراتورهای `@mcp.tool()` و `@mcp.resource()` همان شکل قبلی را دارند، ولی `host` و `port` حالا فقط به `run()` داده می‌شوند، نه به سازندهٔ کلاس. پیش از شروع، [مستندات رسمی SDK پایتون MCP](https://py.sdk.modelcontextprotocol.io/) را برای نسخهٔ روز چک کنید.

### تست با MCP Inspector پیش از اتصال

پیش از اینکه سرور را به هیچ مدلی وصل کنید، آن را با MCP Inspector، ابزار رسمی تست، امتحان کنید:

```bash
mcp dev server.py
```

این فرمان رابط وب Inspector را باز می‌کند (به Node.js نیاز دارد). فهرست ابزارها، schema و توضیح هر کدام را می‌بینید و می‌توانید `get_order_status` را با ورودی `A-1042` اجرا کنید. اگر توضیحی اینجا مبهم است، برای مدل هم مبهم است.

### وصل کردن به Claude

**به Claude Code، به شکل سرور محلی:**

```bash
claude mcp add --transport stdio orders -- python /absolute/path/to/server.py
claude mcp list
```

هرچه بعد از `--` بیاید، بی‌تغییر به عنوان فرمان اجرای سرور استفاده می‌شود. اگر می‌خواهید سرور برای همهٔ اعضای تیم در یک پروژه تعریف شود، با `--scope project` آن را در فایل `.mcp.json` ریشهٔ پروژه ثبت کنید. این فایل را می‌شود دستی هم نوشت و در مخزن گذاشت:

```json
{
  "mcpServers": {
    "orders": {
      "command": "python",
      "args": ["/absolute/path/to/server.py"],
      "env": {
        "ORDERS_DB_URL": "${ORDERS_DB_URL}"
      }
    }
  }
}
```

مقدار متغیرهای محیطی با `${VAR}` از محیط خوانده می‌شود، پس رمز و آدرس پایگاه داده داخل فایل مخزن نمی‌نشیند. Claude Code پیش از استفاده از سرورهای تعریف‌شده در `.mcp.json` از کاربر تأیید می‌گیرد. Claude Desktop هم ساختار مشابهی با کلید `mcpServers` در فایل تنظیمات خودش دارد.

**به Claude API، به شکل سرور راه‌دور:** سرور را با `python server.py --http` اجرا کنید، پشت یک reverse proxy با گواهی HTTPS بگذارید و احراز هویت با توکن را روی آن فعال کنید. سرور نمونهٔ بالا احراز هویت ندارد و فقط برای تست است. وقتی آدرس `https://.../mcp` آماده شد، همان را در `mcp_servers` نمونه‌کد کانکتور بگذارید.

## امنیت MCP: آنچه تیم باید جدی بگیرد

اتصال مدل به ابزار یعنی متن مدل به عمل در دنیای واقعی تبدیل می‌شود. MCP این اتصال را آسان کرده و سطح حمله را هم بزرگ‌تر.

### prompt injection از مسیر خروجی ابزار

هر چیزی که ابزار برمی‌گرداند، مثل متن یک ایمیل یا یک صفحهٔ وب، وارد زمینهٔ مدل می‌شود. اگر کسی در آن متن دستوری کار گذاشته باشد («همهٔ تیکت‌های باز را ببند»، «این فایل را به این آدرس بفرست»)، مدل ممکن است آن را با دستور کاربر اشتباه بگیرد. به این حمله تزریق پرامپت (prompt injection) غیرمستقیم می‌گویند و خطرش وقتی بیشتر است که یک گفت‌وگو هم دادهٔ حساس ببیند و هم ابزار ارسال به بیرون داشته باشد. خروجی ابزار را همیشه داده بدانید، نه دستور، و ابزارهای خواندن از منابع نامطمئن را با ابزارهای نوشتن حساس در یک جلسه کنار هم نگذارید.

### سرور شخص ثالث یعنی کد شخص ثالث

سرور MCP محلی برنامه‌ای کامل است که با دسترسی‌های کاربر اجرا می‌شود و نصبش از مخزنی ناشناس همان ریسکی را دارد که نصب یک بستهٔ ناشناس npm یا pip: ریسک زنجیرهٔ تأمین (supply chain). سرور راه‌دور هم داده‌های شما را می‌بیند و توضیح ابزارهایش، که مستقیم به مدل می‌رسد، می‌تواند دستور پنهان داشته باشد. چون فهرست ابزارها پویاست، سرور سالم امروز ممکن است فردا ابزار تازه‌ای اضافه کند. پس سرورها را مثل وابستگی‌های کد بازبینی کنید، نسخه را ثابت کنید و فقط از منبع رسمی سرویس یا کد بازبینی‌شدهٔ خودتان نصب کنید.

### کمترین دسترسی، allowlist ابزار و تأیید انسانی

- **کمترین دسترسی (least privilege):** سرور سفارش‌ها با کاربر فقط‌خواندنی پایگاه داده کار کند، نه با کاربر مدیر. توکن Jira فقط به پروژه‌های لازم دسترسی داشته باشد.
- **allowlist ابزار:** در کانکتور API با `default_config` و `configs` فقط ابزارهای لازم را فعال کنید. در کلاینت خودتان هم فهرست ابزارهای مجاز را صریح نگه دارید.
- **تأیید انسانی برای نوشتن:** هر ابزاری که چیزی را تغییر می‌دهد، پول جابه‌جا می‌کند، پیام می‌فرستد یا داده‌ای را حذف می‌کند، پیش از اجرا تأیید کاربر بخواهد. در کانکتور API، که فراخوانی سمت سرور انجام می‌شود، ساده‌ترین راه این است که ابزارهای نوشتن را اصلاً فعال نکنید و آن‌ها را از مسیر tool use معمولی در کد خودتان، با مرحلهٔ تأیید، اجرا کنید.
- **لاگ و ممیزی:** هر فراخوانی ابزار، با ورودی و نتیجه و کاربر، ثبت شود تا اگر اتفاقی افتاد بشود ردش را گرفت.

### کلید و توکن سرور کجا بماند

توکن سرورهای MCP همان قواعد [امنیت کلید و توکن API](/blog/api-key-security/) را لازم دارد: در متغیر محیطی یا secret manager، نه در کد و نه در فایل مخزن؛ توکن جدا برای هر سرور و هر محیط؛ دامنهٔ دسترسی محدود و تاریخ انقضا؛ و برنامهٔ چرخش. در کانکتور API، توکن را در کد بک‌اند از محیط بخوانید و هرگز آن را به مرورگر یا اپ موبایل نفرستید. اگر توکن OAuth است، تمدیدش را خودکار کنید تا کسی آن را با توکن بلندمدت پرقدرت‌تر عوض نکند.

## کی MCP بسازیم و کی نه؟

MCP ابزار خوبی است، ولی برای هر مسئله‌ای لازم نیست. این جدول کمک می‌کند تصمیم بگیرید:

| وضعیت | پیشنهاد |
|---|---|
| یک اپلیکیشن، دو یا سه تابع اختصاصی | tool use معمولی در کد خودتان کافی است |
| یک قابلیت که در چند برنامه یا چند تیم لازم است | سرور MCP بسازید |
| سرویسی که سرور MCP رسمی دارد و بازبینی‌اش کرده‌اید | از همان استفاده کنید، با allowlist و کمترین دسترسی |
| محصولی روی Claude API که باید به سرور راه‌دور وصل شود و فقط ابزار لازم دارد | MCP connector |
| نیاز به سرور محلی، منابع، پرامپت‌ها یا کنترل کامل اتصال | کلاینت MCP خودتان با SDK |
| عملیات حساس مالی یا حذف داده | ابزار اختصاصی در کد خودتان با تأیید انسانی، نه سرور عمومی |

### چک‌لیست پذیرش MCP در تیم

- [ ] فهرست سرورهای مجاز تیم مکتوب است و هر سرور یک مالک مشخص دارد.
- [ ] هر سرور شخص ثالث پیش از نصب بازبینی شده، از منبع رسمی آمده و نسخه‌اش ثابت است.
- [ ] هر سرور با کمترین دسترسی لازم کار می‌کند و توکن اختصاصی خودش را دارد.
- [ ] توکن‌ها در secret manager یا متغیر محیطی‌اند و برنامهٔ چرخش و انقضا دارند.
- [ ] در محیط تولید فقط ابزارهای allowlist‌شده فعال‌اند.
- [ ] ابزارهای نوشتن و حذف بدون تأیید انسانی اجرا نمی‌شوند.
- [ ] خروجی ابزارها داده فرض می‌شود و ابزار خواندن از منبع نامطمئن کنار ابزار ارسال داده نیست.
- [ ] هر سرور جدید پیش از اتصال با MCP Inspector تست می‌شود.
- [ ] فراخوانی ابزارها لاگ می‌شود و تغییر ابزارهای هر سرور، مثل تغییر کد، بازبینی می‌شود.

> **خلاصه:** MCP مسئلهٔ N×M اتصال را با یک استاندارد باز حل می‌کند. مدل هنوز از طریق tool use تصمیم می‌گیرد و MCP فقط عرضهٔ ابزار را استاندارد می‌کند. از Claude با اپ‌های آماده، MCP connector در API یا کلاینت خودتان به سرورها وصل می‌شوید، و در هر سه حالت امنیت با کمترین دسترسی، allowlist و تأیید انسانی شروع می‌شود.

کلاود ایران در طراحی پیش‌عرضهٔ خود روی کلید پروژه‌محور، بودجه و گزارش مصرف برای تیم‌ها تمرکز کرده است؛ شرح [قابلیت‌های طراحی‌شده](/#features) در صفحهٔ اصلی آمده و راه‌اندازی آن به قطعی شدن تأمین مورد تأیید و قرارداد بستگی دارد.

## سؤالات متداول

### MCP چیست و آیا جای API را می‌گیرد؟
MCP پروتکلی باز است برای اینکه ابزارها و داده‌ها یک بار و به شکل استاندارد در اختیار برنامه‌های هوش مصنوعی قرار بگیرند؛ لایه‌ای روی APIهای موجود است، نه جایگزین آن‌ها. سرور MCP معمولاً همان API سیستم شما را صدا می‌زند و فقط آن را به شکلی استاندارد در اختیار برنامه‌های هوش مصنوعی می‌گذارد. برای اتصال یک برنامه به یک سرویس، فراخوانی مستقیم API هنوز ساده‌ترین راه است.

### MCP فقط با Claude کار می‌کند؟
نه. MCP استانداردی باز است که Anthropic معرفی کرد و حالا زیر نظر بنیاد Agentic AI Foundation در Linux Foundation نگه‌داری می‌شود. ابزارها، IDEها و ارائه‌دهندگان دیگر هم آن را پشتیبانی می‌کنند. جزئیات پشتیبانی هر محصول را از مستندات خودش چک کنید.

### برای استفاده از MCP حتماً باید سرور بسازم؟
نه. برای بسیاری از سرویس‌های رایج سرور آماده وجود دارد و می‌توانید آن را به Claude Code، Claude Desktop یا کانکتور API وصل کنید. ولی هر سرور شخص ثالث کدی است که به داده‌های شما دسترسی دارد. پس آن را مثل یک وابستگی نرم‌افزاری بازبینی کنید، نسخه‌اش را ثابت نگه دارید و فقط از منبع رسمی نصب کنید.

### فرق MCP با function calling چیست؟
Function calling یا tool use سازوکار خود مدل است: مدل اعلام می‌کند کدام تابع را با چه ورودی صدا بزنید. MCP استانداردی برای عرضهٔ همان تابع‌هاست، تا یک بار در یک سرور تعریف شوند و هر برنامه‌ای بتواند از آن‌ها استفاده کند. در عمل، مدل ابزارهای MCP را هم از طریق همان سازوکار tool use صدا می‌زند.

### آیا MCP امن است؟
خود پروتکل نه امن است و نه ناامن؛ امنیت به پیاده‌سازی و دسترسی‌ها بستگی دارد. خطرهای اصلی تزریق پرامپت از مسیر خروجی ابزار، سرورهای شخص ثالث نامطمئن و توکن‌هایی با دسترسی بیش از حد است. کمترین دسترسی، فعال کردن فقط ابزارهای لازم و تأیید انسانی برای عملیات نوشتن این ریسک را بسیار کم می‌کند.
